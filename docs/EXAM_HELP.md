# 📚 Шпаргалка к защите ЛР (1-4)

## ЛР №1: Протокол TCP
1. **Установление соединения:** 3-way handshake (SYN -> SYN-ACK -> ACK).
2. **Разрыв соединения:** 4-way handshake (FIN -> ACK, FIN -> ACK).
3. **Скользящее окно:** Механизм управления потоком. Позволяет слать пачку данных без ожидания ACK на каждый байт.
4. **Алгоритм Нэгла:** Собирает мелкие пакеты в один большой. Уменьшает оверхед, но увеличивает задержки.
5. **Срочные данные (Urgent Data):** Байт, который летит "вне очереди". Мы юзаем для передачи прогресса.

## ЛР №2: Протокол UDP (Reliable)
1. **Оптимальный буфер (1400 байт):** Ethernet MTU = 1500. Вычитаем IP (20) и UDP (8) заголовки. 1400 — безопасный размер без фрагментации.
2. **Надежность:** Мы сами реализовали ACK (подтверждения) и Retries (повторы при потере).
3. **Скорость:** UDP быстрее TCP на Wi-Fi, так как не тратит время на контроль заторов и медленный старт.

## ЛР №3: Мультиплексирование
1. **NIO Selector:** Позволяет одному потоку следить за сотнями сокетов.
2. **Преимущество:** Нет затрат на переключение контекста между тысячами потоков. Экономия памяти.

## ЛР №4: Пул потоков (Вариант 5)
1. **Преимущества/недостатки процессов:**
   - **Плюсы:** Изоляция (крах одного не валит других), безопасность.
   - **Минусы:** Дорогое создание и переключение контекста, сложное IPC.
2. **Порождение по запросу (on-demand):**
   - **Плюсы:** Ресурсы не тратятся в простое.
   - **Минусы:** Задержка при подключении (пока поток создастся), риск "упасть" под лавиной запросов.
3. **Защита accept:** 
   - Нужна для предотвращения "эффекта бешеной толпы" (Thundering Herd), когда все потоки просыпаются на один `accept()`. 
   - В Варианте 5 (Parallel call) мы полагаемся на то, что современное ядро ОС само эффективно распределяет соединения.
4. **Зачем файл для защиты accept:** Когда сервер на процессах (`fork`), нужен межпроцессный замок (`flock`) на общем файле, чтобы только один процесс заходил в `accept`.
5. **Мультисервисный сервер:** 
   - Либо один процесс слушает много портов (разные сервисы на разных портах), либо диспетчер (inetd) перенаправляет трафик.
6. **Суперсервер inetd:** Демон, который слушает все порты. При входящем соединении запускает нужную программу (например, `ftpd`) и отдает ей сокет.
7. **MSG_PEEK:** Флаг `recv`, позволяющий "подсмотреть" данные в буфере сокета, не удаляя их. Полезно для разбора заголовков, если неясно, какой протокол пришел.
8. **Thread Pool (Динамика):** Nmin — база, Nmax — потолок. Пул растет при нагрузке и сжимается при простое (Idle Timeout).
